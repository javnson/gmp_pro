# GMP Core 架构与维护指南

## 入口与覆盖顺序

`gmp_type.h` 是轻量标准入口，负责组合用户配置、CSP 配置和仓库默认值。
覆盖优先级是：用户配置 > CSP 配置 > GMP 默认配置。`gmp_core.h` 在此基础
上继续装配 base、dev、可选 mm/CTL 和 rt。

## 分层边界

- `std` 只定义标准和选择规则，不承载调度、外设实现或完整运行框架。
- `base` 提供不依赖完整运行时的基础服务、时钟契约和数据结构。
- `mm`、`pm` 是重要的基础能力，保持独立选择和注册。
- `dev` 只处理外设类型、HAL 契约、具体驱动和外设数据链路。
- `rt` 才允许组合 CSP 生命周期、用户入口、CTL 和完整 GMP 服务。

禁止形成从低层到高层的反向依赖。例如 `std` 不得包含 `dev` 或 `rt`，
`base` 不得依赖具体驱动。

## Facility 管理

权威注册表是
`tools/facilities_generator/src_mgr/gmp_framework_dic.json`。项目中的
`gmp_framework_config.json` 是项目拥有的选择输入；`gmp_inc`、`gmp_src`
以及 Keil/CCS 中由管理器引入的副本都是生成输出，不应反向修改仓库源码。

新增或迁移模块时必须同步：物理路径、模块 ID、依赖、项目选择配置、外设
扫描器和生成验证。源文件会被扁平复制到 `gmp_src`，因此不同模块不能使用
重复的 `.c/.cpp` 文件名。

## README 维护规则

1. 当前目录 README 只说明本层职责、公开入口和下级索引。
2. 具体 API、配置宏和验证状态写在最接近实现的模块 README 中。
3. 上层使用相对链接引用下层，不复制大段子模块文档。
4. 文件移动时同时更新 README、Facility 注册表和源码引用。
5. 未实现模块必须明确标记为占位，并且不得注册成可用设施。
