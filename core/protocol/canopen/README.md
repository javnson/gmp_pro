# GMP CANopen core

This directory provides a portable, allocation-free CANopen protocol core. It models
classic CAN frames, NMT/heartbeat, an RB-tree object dictionary, an SDO server,
compiled PDO mappings, and a normalized CANopen over EtherCAT (CoE) service boundary.
The complete-node facade owns the protocol engines and the interrupt/background queues;
hardware CAN/EtherCAT transfer, filtering, mailbox encoding, and wake-up scheduling
remain the responsibility of the CSP/application adapter.

## Modules

| Facility ID | Files | Contract |
| --- | --- | --- |
| `core|protocol|canopen|base` | `can_if.h` | Classic-CAN frame and normalized request types. `gmp_canopen_decode_frame()` and `gmp_canopen_encode_request()` intentionally remain adapter contracts without a default implementation. |
| `core|protocol|canopen|nmt` | `nmt_sm.h`, `src/nmt_sm.c` | Node NMT command handling, boot-up/producer heartbeat, and heartbeat consumer timeout. |
| `core|protocol|canopen|od` | `od.h`, `src/od.c` | Object dictionary indexed by `(index, sub-index)` using the intrusive RB tree. Entries can own an inline scalar/8-octet union or point at application storage. |
| `core|protocol|canopen|sdo` | `sdo_engine.h`, `src/sdo_engine.c` | Server-side expedited and segmented upload/download with standard abort frames. |
| `core|protocol|canopen|pdo` | `pdo_engine.h`, `src/pdo_engine.c` | Compiles separate TXPDO/RXPDO plans once, then performs lookup-free online packing/unpacking; sorted groups organize multiple PDOs. |
| `core|protocol|canopen|coe` | `ethercat_if.h`, `src/ethercat_if.c` | Reuses the OD, SDO abort model, and compiled PDO plans behind a normalized CoE adapter boundary. |
| `core|protocol|canopen|node` | `canopen.h`, `src/canopen.c` | Complete node, common CAN/CoE packet contract, CiA 301 base objects, bounded SPSC input/output queues, and the transport/background callbacks. |
| `core|protocol|canopen|cia301`, `cia401`, `cia402` | profile `.eds` and generated `gmp_cia*_od.[ch]` | Independently usable GMP profile-seed dictionaries generated by `canopen_eds_cc`. |

## Complete node and adapter contract

An application normally declares one `gmp_canopen_t`. `gmp_canopen_init()` connects its
NMT, SDO, PDO, and CoE engines to one OD and registers pointer-backed CiA 301 objects:
`0x1000`, `0x1001`, `0x1017`, `0x1018:00..04`, and optional strings
`0x1008..0x100A`. Application/profile objects and compiled PDO plans can then be added to
the node-owned dictionary and direction-specific PDO groups.

`gmp_canopen_packet_t` is the public transport boundary. CAN adapters use
`GMP_CANOPEN_PACKET_CAN_FRAME` with `key` as the CAN identifier. EtherCAT adapters use
the normalized CoE SDO/PDO kinds with `index/subindex`, request `number`, PDO `key`, and
owned `byte_gt` payload. Raw EtherCAT mailbox headers are deliberately outside this
contract.

The runtime flow is fixed:

1. A CAN RX ISR or EtherCAT callback calls `gmp_canopen_input_callback()`. It validates
   and copies the input; it does not parse the protocol or touch the OD.
2. The main loop calls `gmp_canopen_background_callback(elapsed_ms)`. It advances the
   heartbeat, dispatches queued CAN/CoE requests, updates NMT/RPDO state, and queues SDO,
   heartbeat, or TPDO output.
3. A CAN-idle ISR, DMA feeder, or EtherCAT adapter calls
   `gmp_canopen_output_callback()` until it returns `GMP_CANOPEN_NODE_EMPTY`.

Each queue is bounded and reserves one physical slot, so usable capacity is
`GMP_CANOPEN_QUEUE_SLOTS - 1`. This is an SPSC contract: the input callback is the only
RX producer, the background callback is the RX consumer and TX producer, and the output
callback is the only TX consumer. Call `gmp_canopen_publish_tpdo()` from the same
background/TX-producer context, not from a second ISR. Queue depth, packet payload, and
per-call processing budget are compile-time configurable. The portable implementation
targets a single-core ISR/main-loop pair; `volatile` indexes are not a multicore memory
barrier, so a multicore adapter must provide serialization or platform fences.

## Eight-bit wire data on C28x

`gmp_canopen_octet_t` deliberately does not exist. A CANopen wire octet and a C object
called a byte are different concepts on a target such as C28x, where `CHAR_BIT` is 16.
The portable protocol core therefore uses the following single representation policy:

| Data kind | Portable representation | Rule |
| --- | --- | --- |
| CAN frames, serialized SDO/PDO buffers, strings, and domains | `byte_gt` elements | Each element carries one wire octet. `byte_gt` is compile-time checked as unsigned; values above `0xFF` are rejected when its native width can represent them. |
| CiA `INTEGER8` / `UNSIGNED8` scalar values | `int_least8_t` / `byte_gt` | These types may occupy 16 C bits on C28x, but serialization still enforces the CiA 8-bit range. |
| Packed host/driver buffers | `uint8_t` adapter helpers | Available only when `UINT8_MAX` exists and `CHAR_BIT == 8`; a C28x driver uses the logical-cell API directly. |

This avoids parallel u8/u16 implementations of OD, NMT, SDO, and PDO. The hardware or
EtherCAT-stack adapter is the only representation boundary. Multi-octet values are
always serialized explicitly in little-endian order.

## PDO execution model

TXPDO and RXPDO have distinct plan types. Compilation validates every mapping, resolves
the OD entry and storage address, selects the scalar/raw codec, and calculates the byte
offset once. The `_fast` online functions then access those resolved addresses directly;
they do not search the RB tree or recompile the mapping. The referenced OD entry and its
storage address must therefore remain alive and unchanged for the plan lifetime. Rebind
an OD pointer only after stopping online traffic, then compile the plan again.

Classic-CAN compile entry points enforce the 8-octet payload and 11-bit COB-ID. Buffer
compile entry points support larger process-data images for CoE. Sorted TXPDO/RXPDO
groups provide indexed TX construction and binary-search RX dispatch without merging
the direction-specific state machines.

## Deliberate boundaries

- The SDO implementation is a server. The transfer staging limit defaults to 128 octets
  and can be changed with `GMP_CANOPEN_SDO_MAX_TRANSFER`.
- PDO mappings must be byte-aligned and exactly match an OD entry width. Classic CAN
  plans must fit eight octets; CoE buffer plans may use a caller-selected larger capacity.
  Bit-level packing, CAN FD, SYNC scheduling, inhibit/event timers, EMCY, TIME, LSS, and
  a CiA 402 drive state machine are not yet implemented.
- `canopen.h` does not bind to `core/dev/can` or a particular EtherCAT stack. The node
  owns protocol queues, while an application adapter moves public packets to/from the
  selected peripheral or mailbox implementation.
- OD entry objects are intrusive and may belong to only one dictionary at a time. The
  generated profile dictionaries therefore have one static instance each.
- `ethercat_if` is a normalized service interface, not a raw EtherCAT mailbox codec.
  The selected EtherCAT stack owns mailbox headers/counters, fragmentation, and AL-state
  gating. CoE Complete Access and SDO Information are not yet implemented.

CoE follows the EtherCAT model in which CANopen OD, SDO, and PDO mechanisms are reused,
while the legacy eight-octet PDO restriction may be relaxed for EtherCAT process data:

- EtherCAT Technology Group, protocol overview: <https://www.ethercat.org/en/technology.html?trk=public_post_comment-text>
- ETG.1500 master classes: <https://www.ethercat.org/download/documents/ETG1500_V1i0i2_D_R_MasterClasses.pdf>
- ETG.2200 implementation guide: <https://www.ethercat.org/download/documents/ETG2200_V3i2i2_G_R_EtherCATImplementationGuide.pdf>

## EDS provenance

An EDS describes one concrete device under CiA 306-1; CiA does not publish a single
generic device EDS for each profile. CiA 301 v4.2.0 and the CiA 401/402 profile documents
are licensed member/download material, and official conformance object databases are
distributed with CiA tools. Consequently, the three committed `.eds` files are explicit
**GMP-maintained profile seeds**, not verbatim CiA or vendor EDS files and not a
conformance claim. They contain the common communication objects plus representative
401 I/O or 402 drive objects so that generation and integration can be tested. A shipping
product must replace identity data and complete all supported device-specific objects.

References:

- CiA 306 EDS overview: <https://www.can-cia.org/can-knowledge/cia-306-series-electronic-device-description-edd>
- CiA 401 profile overview: <https://www.can-cia.org/can-knowledge/cia-401-series-i/o-device-profile>
- CiA 402 profile overview: <https://can-cia.org/can-knowledge/cia-402-series-canopen-device-profile-for-drives-and-motion-control>
- CiA conformance tool/CODB note: <https://www.can-cia.org/services/where-is-the-eds-checker-gone>

## Regenerate dictionaries

Run from the repository root with Python 3.10 or newer:

```powershell
python tools/protocol_mgr/canopen_eds_cc/canopen_eds_cc.py core/protocol/canopen/cia301/cia301.eds --output-dir core/protocol/canopen/cia301 --name gmp_cia301_od --storage pointer --node-id 1
python tools/protocol_mgr/canopen_eds_cc/canopen_eds_cc.py core/protocol/canopen/cia401/cia401.eds --output-dir core/protocol/canopen/cia401 --name gmp_cia401_od --storage pointer --node-id 1
python tools/protocol_mgr/canopen_eds_cc/canopen_eds_cc.py core/protocol/canopen/cia402/cia402.eds --output-dir core/protocol/canopen/cia402 --name gmp_cia402_od --storage pointer --node-id 1
```

`--node-id` resolves `$NODEID` expressions in communication-object defaults. Pointer
storage is the normal application choice because the generated variables remain visible
and writable from a debugger. Inline value storage is useful for small private values.
